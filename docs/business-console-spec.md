## 1. 왜 만들었나

시설은 이미 공공데이터로 돌보다에 페이지가 있다(전국 2만 8천여 곳). 문제는 **그 페이지를 시설이
직접 관리할 방법이 없었다**는 것 — 소개글도, 사진도, 상담 신청 수신처도 없었다.

기업회원은 이 페이지의 운영 주체가 되는 절차다. 서류 확인(전화 없음, §5) 후 계정을 연결하면
[기업회원 콘솔](#3-콘솔-devbusinessconsole)에서 자기 시설 페이지를 직접 관리한다.

**명칭**: 이 기능의 이용 주체는 원래 "시설 운영자"로 불렸으나 2026-08-04에 **"기업회원"으로
전면 개칭**했다(§7). 단, **정보 정정 요청**(§3-6) 관련 문구는 "시설 운영자"를 그대로 쓴다 —
그 기능은 "이 계정이 이 시설의 실제 운영자라서 원본 데이터를 더 잘 안다"는 맥락이 핵심이라,
계정 유형을 가리키는 "기업회원"보다 그 관계를 직접 가리키는 표현이 더 맞다는 판단(사용자 결정).

## 2. 가입 절차 요약

전체는 [lib/businessPlans.ts](../lib/businessPlans.ts)의 `SIGNUP_STEPS`, 화면은
`/business` → `/business/apply` → (이메일 서류 확인, 운영자 승인) → `/business/console`.

| 단계 | 누가 | 무엇을 |
|---|---|---|
| 신청 | 기업회원 후보 | `/business/apply` — 시설명·기관기호(또는 사업자등록번호)·담당자 연락처 (§`app/api/business-inquiry/route.ts`) |
| 서류 확인 | 운영자 → 기업회원 | 이메일로 지정서/사업자등록증 사본 요청·회신 (**전화 없음** — 운영 방침) |
| 승인 | 운영자(`/admin`) | `FacilityOwner` 생성 + 유료 상품이면 `FacilitySubscription`(pending) + 스폰서/배너면 `SponsorPlacement`/`FacilityBanner` 슬롯 예약을 **한 트랜잭션**으로 (`app/api/admin/inquiries/route.ts`). 슬롯에는 **그 구독의 id를 물린다**(§2-2) |
| 이용 시작 | 기업회원 | `/business/console`에 자기 시설이 뜬다 |

승인 로직은 지역당 스폰서 슬롯(`SPONSOR_SLOTS_PER_SIGUNGU`=3)·배너 슬롯(`BANNER_SLOTS_PER_SIGUNGU`=1)
상한을 지킨다 — "지역당 N곳"이라는 공개 약속이 여기서 지켜진다.

### 2-1. 슬롯 상한은 두 시점에서 지킨다 (2026-08-06)

**자리를 세는 기준은 "노출 중"이 아니라 "자리를 잡고 있는가"다.** 승인이 만드는 슬롯은
입금 대기라 `active=false`인데, 이걸 빈자리로 세면 같은 자리를 두 번 판다.

| 시점 | 어디서 | 무엇을 세나 |
|---|---|---|
| **판매(승인)** | `admin/inquiries` → `remainingSlots()` | 자리 점유분 전부 — 입금 대기·일시중지 포함, 해지·기간만료 제외 |
| **노출 시작(입금 확인)** | `admin/subscriptions` PATCH | **지금 실제 노출 중인 것만**(`onlyActive`) |

두 시점이 다 필요하다. 승인은 여러 건이 먼저 쌓일 수 있고(전부 입금 대기), 켜는 건
나중에 하나씩이기 때문이다. 활성화 시점에 안 막으면 상한을 넘겨 노출되거나 —
더 나쁘게는 — `lib/sponsor.ts`의 `take` 상한에 걸려 **나중에 계약한 시설이 돈을 내고도
조용히 노출 0**이 된다(월간 보고서에도 0으로 찍힌다).

자리를 비우는 것은 **해지뿐**이다(`endsAt`이 찍힌다). 일시중지는 잠깐 끄는 것이라
자리를 계속 잡고 있다.

### 2-2. 광고를 켜고 끄는 단위는 시설이 아니라 구독 (2026-08-06)

`SponsorPlacement`·`FacilityBanner`에 **`subscriptionId`**가 있다. 한 시설이 여러 지역을
살 수 있어서(스키마 주석 참조) 시설 단위로 껐다 켜면 **아직 유효한 다른 지역 계약까지
같이 꺼진다.** `admin/subscriptions` PATCH는 이 구독이 산 슬롯만 건드린다.

### 2-3. 해지는 되돌리지 않는다 (2026-08-06)

`cancelled` 구독은 되살릴 수 없다(PATCH가 409). 되살리려면 `endsAt`을 지워야 하는데
그 값이 "언제까지 노출됐는가"의 정산 근거라, 지우는 순간 근거가 사라지기 때문이다.
재계약은 **새 신청 → 새 승인 → 새 구독 행**이다(계약 시점 금액도 그때 값으로 복사되는 게 맞다).

같은 이유로 `endsAt`은 **해지일 때만** 쓴다. 예전에는 해지가 아닌 모든 전이에서 `null`로
덮어써, 기한이 정해진 구독을 일시중지했다 켜는 것만으로 기한이 사라졌다.

## 3. 콘솔 (`/business/console`)

`app/business/console/page.tsx`(서버, `force-dynamic`)가 로그인한 사용자의 `myFacilities()`를
조회해 `ConsoleClient`(클라이언트)에 넘긴다. 시설이 0곳이면 안내+신청 유도 화면만 보여준다.

### 3-1. 시설 여러 곳 — 탭 전환 + 합산 개요

한 계정(`userId`)이 `FacilityOwner` 행을 여러 개 가지면 시설을 여러 곳 관리하는 것이다
(이미 지원되던 구조 — 승인 로직이 `facilityId+userId` 조합으로 upsert한다). 화면은:

- **시설이 1곳**: 탭도, 합산 개요도 안 보인다 — 대부분이 이 경우라 화면을 안 늘린다.
- **시설이 2곳 이상**: `CompanyOverview` 섹션(2026-08-04 신설, `ConsoleClient.tsx`)이 탭
  위에 먼저 뜬다. 조회수·상담 신청을 전 시설 합산해서 보여준다 — 예전엔 탭을 오가며
  머릿속으로 더해야 했다.

### 3-2. 대시보드 숫자 — 조회수·상담

시설당: 페이지 조회(7일/30일), 상담 신청(30일/전체). 서버(`page.tsx`)가
`FacilityDailyView`·`ConsultRequest`를 병렬로 모아 계산한다.

**"지난 30일 대비" 증감 배지**(2026-08-04 신설, `Delta` 컴포넌트) — 조회수·상담 30일 통계
옆에 ▲/▼ %(또는 "신규")가 붙는다. 서버가 60일치를 받아 최근 30일 vs 그 이전 30일로
나눠 계산한다(`page.tsx`의 `prevMonthAgo`). 계산 자체는 [lib/deltaPct.ts](../lib/deltaPct.ts)의
`pctDelta()`를 쓰는데, 이 함수는 [월간 성과 보고서](#4-월간-성과-보고서-devbusinessconsolereport)의
"지난달 대비" 계산과 **같은 함수를 공유**한다(원래 각자 구현하고 있던 걸 2026-08-04에 합쳤다).

색 규칙: 증가=민트(좋음), 감소=`ink-400`(중립 회색), 이전 구간이 0이면 "신규" 배지. 이
앱의 accent/danger 톤은 행정처분·경고 같은 실제 위험 신호 전용이라, 트래픽이 준 정도에
빨간색을 쓰면 과하게 읽힌다는 판단으로 danger 톤을 안 썼다.

### 3-3. 최근 30일 조회 추이 (`ViewTrendChart`)

[components/ViewTrendChart.tsx](../components/ViewTrendChart.tsx) — 콘솔과 월간 성과
보고서가 공유하는 막대 그래프(2026-08-04 통합, §7). 외부 차트 라이브러리를 안 쓰고
div로 직접 그린다(담당자가 폰으로 보는 화면이라 무거운 라이브러리가 안 맞는다는 원칙,
`businessPlans.ts`·이 컴포넌트 주석에 반복해서 나오는 판단).

막대 하나하나가 탭·호버 가능한 `<button>`이라 그날 정확한 숫자가 캡션에 뜬다(기본값은
마지막 날=오늘). **주의**: `series`의 `date`는 이미 화면에 보여줄 라벨("8/4")이어야
한다 — 호출부마다 원본 날짜 형식이 다르다(콘솔은 ISO "YYYY-MM-DD"를 `formatDay()`로
변환해서 넘기고, 월간 보고서는 `lib/monthlyReport.ts`의 `last30DaysSeries()`가 이미
"M/D" 형식으로 만들어 넘긴다).

### 3-4. 소개글·사진·배너·소식

플랜별 상한(§6)을 넘지 않는 선에서 시설이 직접 쓴다. 저장은 전부 명시적 버튼(자동저장
아님 — "저장된 건가?" 불안을 안 만든다는 원칙). 관련 API: `/api/business/content`
(소개글), `/api/business/photos`, `/api/business/banner`, `/api/business/posts`.

### 3-5. 최근 상담 신청

`ConsultRequest`를 시설별로 최신 10건까지 보여준다. 보호자가 직접 남긴 연락처라 "상담
목적으로만 사용"을 명시한다.

### 3-6. 정보 정정 요청

`/api/business/correction` — 시설 운영자가 공공데이터 항목(인력·정원·연락처 등)이 실제와
다르면 접수한다. **시설이 직접 고치지 않는다** — 그 값들은 안심지수·필터의 입력이라
시설 손에 맡기면 지표 신뢰가 무너진다는 판단. 접수만 받고 운영자가 원본과 대조해 반영한다.

### 3-7. 확장 상품 안내

가격은 **여기(인증된 기업회원만 보는 화면)에서만** 보여준다. `/business`(공개 랜딩)는
무료 혜택 중심이고 가격표를 안 내민다 — "결국 돈 내라는 거네"로 읽혀 신청 자체가 주는 걸
막기 위해서다(`app/business/page.tsx` 주석).

## 4. 월간 성과 보고서 (`/business/console/report`)

지역 프리미엄 이상 전용(`capabilityOf(plan).hasReport`). `lib/monthlyReport.ts`의
`getMonthlyReport()`가 **KST 캘린더 월** 기준으로 이번 달·지난달을 비교한다(콘솔의 "최근
30일 대비"와는 다른 창 — §5 참고).

- 조회수·상담 신청: 이번 달/지난달 + `pctDelta()` 증감 + 지역 평균 대비 배수
  (같은 시·군·구 시설이 2곳 이상일 때만 계산)
- 광고 성과(스폰서·배너): 노출·클릭·클릭률 — `sponsor`/`banner`가 null이면 섹션 자체를
  숨긴다("노출 0"과 "아직 측정 안 함"은 다른 뜻이라 섞지 않는다는 원칙)
- 페이지 관리 현황: 소개글 작성 여부·사진 수·이달 발행한 소식 수

## 5. 두 가지 "증감" — 헷갈리지 말 것

같은 화면 계열에 창(window)이 다른 증감 지표가 두 개 있다. 새로 손댈 때 섞어 쓰지 않는다.

| | 창 | 위치 | 이유 |
|---|---|---|---|
| 콘솔의 Delta 배지 | 최근 30일 vs 그 이전 30일(rolling) | `/business/console` | 매일 여는 화면이라 "오늘 기준 최근 추세"가 더 직관적 |
| 보고서의 DeltaBadge | 이번 달 vs 지난달(캘린더) | `/business/console/report` | "월간 보고서"라는 형식 자체가 캘린더 월 단위를 기대하게 만든다 |

두 계산 모두 [lib/deltaPct.ts](../lib/deltaPct.ts)의 같은 `pctDelta()`를 쓰지만, **어느
구간의 합계를 넘기느냐**만 호출부마다 다르다. 이전 구간이 0이면 `null`을 돌려주고,
화면은 그 `null`을 각자 맥락에 맞게 보여준다(콘솔="신규" 배지 / 보고서="지난달 데이터 없음").

## 6. 플랜별 기능 상한 (`capabilityOf()`)

[lib/businessPlans.ts](../lib/businessPlans.ts)의 단일 출처. 화면·API가 전부 이 값을 본다.

| plan id | 사진 상한 | 소식 발행 | 통계 | 월간 보고서 | 지역 배너 |
|---|---|---|---|---|---|
| free | 5장 | ✗ | ✗ | ✗ | ✗ |
| plus | 30장 | ✓ | ✓ | ✗ | ✗ |
| sponsor | 30장 | ✓ | ✓ | ✗ | ✗ |
| premium | 30장 | ✓ | ✓ | ✓ | ✓ |
| silvertown | 30장 | ✓ | ✓ | ✓ | ✓ |

가격·상세 구성은 `lib/businessPlans.ts`의 `BUSINESS_PLANS`가 단일 출처다 — 여기 표는
기능 상한 요약이고, 가격은 이 문서에 옮겨 적지 않는다(가격 변경 시 이 문서까지
갱신해야 하는 이중 관리를 피하려고 — 예전에 사이트 설명의 시설 수가 화면 집계와
어긋났던 사고와 같은 종류를 미리 막는다는 게 `businessPlans.ts` 자신의 원칙이다).

## 8. 알려진 제약 (다음에 손볼 것)

- **정정 요청은 상태 추적이 없다** — 접수 즉시 이메일·텔레그램 알림만 가고, 기업회원 쪽에서
  "처리됐는지" 확인할 방법이 콘솔에 없다(운영자 쪽 `/admin` corrections 탭에서만 본다).
- **입점 신청 중복 방지 없음** — 같은 기관기호로 여러 번 신청해도 계속 새 행이 쌓인다.
- **월간 보고서 지역 평균은 `REGION_SEO` 기준** — `REGIONS`(17개)와의 taxonomy 이중화
  문제(docs/alert-system-spec.md에도 기록된 것과 같은 종류)가 여기도 잠재해 있다.
- **자동 만료 경로가 없다** — 구독은 항상 `endsAt=null`(기한 없음)로 만들어지고, 꺼지는
  경로는 운영자의 수동 해지뿐이다. `activeSubscriptionsFor()`·`lib/sponsor.ts`는 이미
  `endsAt`을 보고 있으니 **값만 채우면 자동으로 만료된다** — 계약 기간을 받는 화면이
  생길 때 같이 붙이면 된다. 지금은 운영자가 잊으면 무기한 노출된다.
- **유료 기능은 아직 프로덕션에서 한 번도 안 돌았다** — `FacilitySubscription`·
  `SponsorPlacement`·`FacilityBanner`·`FacilityPost`·`FacilityContent`·`AdEvent` 전부 0행
  (2026-08-06 실측). 위 슬롯·상태 수정은 **코드와 시나리오 테스트로만 검증**됐고,
  실제 승인→입금 확인→노출→해지를 한 번 통과시켜 본 적은 없다. 첫 고객 전에 할 것.
