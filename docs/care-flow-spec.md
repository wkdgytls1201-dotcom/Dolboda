## 2. 상태 전이 표

굵은 가드는 화면이 아니라 **API가 직접 막는 것**이다(화면에서 버튼을 숨기는 것만으로는
막히지 않는다 — 5차 §3-8 규칙). "알림"은 alert-system-spec의 절 번호.

| 단계 | 요청 | 지원 | 누가 | API | 가드 | 알림 |
|---|---|---|---|---|---|---|
| 요청 등록 | `OPEN` 생성 | — | 보호자 | `POST /api/care-requests` | **진행 중(OPEN·MATCHED) 1건 제한 — 보호자별 advisory xact lock으로 직렬화(409)**, 날짜 역전 400, 유형별 필수값 | §3-7 새 일자리(다음 배치) |
| 매니저 지원 | `OPEN` | `지원완료` 생성 | 매니저 | `POST /api/care-request-applications` | **요청 OPEN만**, **자기 요청 지원 금지**(운영자만 예외 — 종단 테스트용), **중복 지원 unique 409**. 제안 사례비(≤100만원)·한마디(≤200자) 선택, **단위는 지원 시점 고정** | §3-8 보호자(제안 금액·한마디 동봉) |
| 재제안 | `OPEN` | `지원완료` | 매니저 본인 | `PATCH …/applications/[id]` `action=propose` | **본인만**, **지원완료+요청 OPEN만(409)** — 확정 후 바꾸면 합의서 봉인값과 어긋난다 | 없음 |
| 지원 철회 | `OPEN` | (삭제) | 매니저 본인 | `DELETE …/applications/[id]` | **지원완료만(409)** — 확정 뒤엔 보호자가 취소하는 게 맞는 순서 | 없음 |
| 매칭 확정 | `OPEN`→`MATCHED` | `매칭확정` / 나머지 `미선정` | 보호자 | `PATCH …/applications/[id]` `action=confirm` | **보호자만**, **요청 OPEN+지원 지원완료(409)**, **트랜잭션 내 조건부 updateMany로 선점**(동시 확정 경쟁에서 진 쪽 409) | §3-9 확정자, §3-10 미선정 전원(**대상은 트랜잭션 전에 조회** — updateMany는 "누가"를 안 알려줌) |
| 합의서 서명 | `MATCHED` | `매칭확정` | 양측 각자 | `PATCH /api/care-agreement` | 조회 컨텍스트 MATCHED·COMPLETED만, **재서명 409**, **동시 첫 서명 409**(unique 충돌 안내). 첫 서명이 내용 봉인+SHA-256. **확정된 제안 금액이 있으면 그 값을 봉인** | 양측 완료 시 사본 발송(각자 따로) |
| 요청 수정 | `OPEN` | — | 보호자 | `PATCH /api/care-requests/[id]` | **OPEN만(409)**, **날짜 역전 400**(수정에도), 유형별 필수값 재검증 | 없음 |
| 요청 취소 | `OPEN`·`MATCHED`→`CANCELLED` | `지원완료`·`매칭확정`→`요청취소` | 보호자 | `DELETE /api/care-requests/[id]` | **OPEN·MATCHED만(409)** — 완료된 돌봄이 취소로 뒤집히면 매니저 실적이 사라진다. **지원자 상태 함께 정리** | §3-13 지원자 전원(matchUpdate 존중). 취소된 건의 합의서 비노출은 **의도된 동작**(care-agreement-spec §1) |
| 돌봄일지 | `MATCHED`·`COMPLETED` | `매칭확정`·`돌봄완료` | 확정 매니저 | `POST /api/care-log` | `careDate` 형식·미래 날짜 거부, **하루 1원본(409)** — 정정은 `correctsId`로 append-only | §3-12 하루 첫 원본에 보호자(특이사항 메일과 두 통 금지) |
| 돌봄 완료 | `MATCHED`→`COMPLETED` | `매칭확정`→`돌봄완료` | 보호자 | `PATCH /api/care-requests/[id]` `action=complete` | **MATCHED만(409)** | §3-11 매니저 |
| 후기 작성 | `COMPLETED` | `돌봄완료` | 보호자 | `POST /api/care-reviews` | **COMPLETED만**, **요청당 1건(409)**, 실제 돌봄완료된 매니저만, 별점 1~5 정수 | 없음 |

## 3. 역경매 제안 (2026-08-05 도입)

- 지원 시 `proposedAmount`(원)·`proposedUnit`("시간"|"일")·`message`를 선택 입력.
  상한 100만원은 시세 제한이 아니라 **오타(0 하나 더) 방지**다.
- **단위는 지원 시점의 요청 단위를 고정 저장** — 요청이 OPEN 중 수정돼도 제안의
  뜻("하루 9만원")이 뒤집히지 않는다.
- 재제안은 위 표의 조건에서만. 확정되면 합의서가 그 시점 제안 금액을 봉인하므로
  이후 수정 경로가 없어야 기록이 진실로 남는다(care-agreement-spec §1의 ℹ️ 참고).
- 보호자 지원자 카드에는 제안 배지·한마디 인용·성별/연령대·**돌봄일지 기록일 수**
  (원본만 집계 — 하루 1원본 가드 덕에 개수=기록한 날 수)를 함께 보여준다.

## 4. 표 밖의 확정 규칙

1. **지원자 목록은 ⭐ 돌봄 스타(포인트) 활성자 우선, 그 안에서 먼저 지원한 순**
   (2026-08-06 사용자 결정 — 이전의 "선착순만" 원칙을 대체). 정렬을 명시하지 않으면
   DB 내부 순서라 새로고침마다 뒤바뀐다(시나리오 감사 2026-08-05).
2. **지원자 응답은 `APPLICANT_SELECT`로 최소화** — 예전에 sitterProfile 통짜 include로
   정산 계좌가 네트워크 응답에 실려 나갔다. 필드를 늘릴 땐 이 select에만 추가.
3. **부분 유니크 인덱스 금지** — 이 프로젝트는 `db push` 워크플로라 스키마 파일에 못
   적는 DB 객체는 다음 push 때 소리 없이 사라질 수 있다. 동시성은 advisory xact lock
   (요청 등록)·조건부 updateMany(매칭 확정)·unique 제약(중복 지원, 동시 첫 서명) 같은
   스키마에 남는 수단으로만 막는다(14차 §3-2).
4. **상태 변경 성공 "뒤"에만 메일을 시도하고, 발송 실패는 API 응답을 바꾸지 않는다**
   (alert-system-spec §3-13 아래 원칙 참고).
5. `CareAgreement`는 User·CareRequest에 **관계를 걸지 않는다** — 탈퇴 Cascade로
   합의서가 사라지면 남은 당사자가 권리를 증명할 수 없다(care-agreement-spec §2).
