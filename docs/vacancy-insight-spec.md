# 자리 인사이트 — 설계·근거·한계

> 최초 작성: 2026-08-06 · 구현: [lib/vacancyTrend.ts](../lib/vacancyTrend.ts)(시계열),
> [lib/vacancyInsight.ts](../lib/vacancyInsight.ts)(지표),
> [app/facility/[id]/VacancyTrend.tsx](../app/facility/[id]/VacancyTrend.tsx)(화면)
>
> **지표·임계값을 바꾸기 전에 §1과 §4를 읽을 것.** 숫자를 조금만 손대도 "예측"의
> 성격이 바뀌고, 이 기능은 보호자의 실제 결정(대기를 걸지 말지)에 쓰인다.

## 1. 무엇이 자산인가

공단(longtermcare.or.kr)은 **오늘 값만** 공개한다 — 정원·현원·대기 인원의 스냅샷 하나.
어제 값도, 지난달 값도 주지 않는다. 그래서 "이 시설 자리가 잘 나나?", "대기 걸면
얼마나 기다리나?"는 **공개 데이터만으로는 누구도 답할 수 없다.**

돌보다는 2026-08-02부터 매일 그 값을 저장한다(`FacilitySnapshot`,
[scripts/daily-nhis-sync.mjs](../scripts/daily-nhis-sync.mjs)). 쌓인 시계열이
이 문서가 다루는 자산이고, 경쟁 서비스에 없다.

**성격**: 공공데이터를 재가공한 것이 아니라 **시간을 들여야만 생기는** 데이터다.
오늘 시작한 경쟁자는 오늘부터 쌓아야 하고, 우리보다 항상 뒤에 있다.

## 2. 저장 구조와 주의점

| 항목 | 내용 |
|---|---|
| 모델 | `FacilitySnapshot(facilityId, date, capacity, currentOccupancy, waitlistCount, grade)` |
| 유니크 | `[facilityId, date]` — 하루 한 행 |
| 적재 규칙 | **바뀐 시설만** 그날 값으로 적재(용량 절약). 첫 실행일은 전체 기준선 |
| 첫 기준선 | 2026-08-02, 27,493곳 |
| 일일 증가 | 289~394행 수준(변동분만) |

⚠️ **적재가 듬성듬성하다는 점이 이 자산을 다루는 첫 함정이다.** 기록이 없는 날은
"자리 0"이 아니라 "전날과 같음"이다. `buildVacancySeries()`가 마지막 관측값을 다음
관측일까지 이어 붙여(forward-fill) 하루 단위 시계열로 편다. 이걸 건너뛰고 원본 행을
그대로 그리면 그래프가 실제와 정반대로 보인다.

⚠️ 원본에 **현원 > 정원**인 행이 있다(공단 집계 시점 차이). 빈자리를 음수로 두면
막대가 뒤집히므로 0으로 본다.

## 3. 지표 정의

`computeVacancyInsight(series)` — forward-fill된 시계열에서 계산한다.

| 지표 | 정의 | 왜 이렇게 |
|---|---|---|
| `days` | 관측한 날 수 | 모든 지표의 신뢰도 기준 |
| `openings` | 빈자리가 **0 → 양수**로 바뀐 횟수 | 3→5처럼 늘어난 건 같은 자리의 재집계일 수 있어 사건으로 세지 않는다(과대 계상 방지) |
| `fullRatio` | 빈자리 0인 날 / 전체 관측일 | "거의 항상 만실"인지 한 숫자로 |
| `avgVacancy` | 평균 빈자리 수 | |
| `waitPerDay` | 대기 인원 최소제곱 직선 기울기의 **부호를 뒤집은 값** | 양수 = 줄어드는 중. 사람이 읽기 좋은 방향으로 |
| `estimatedWaitDays` | `대기 인원 ÷ waitPerDay` | 조건 충족 시에만(아래) |

### 신뢰도 등급

| 등급 | 관측 일수 | 뜻 |
|---|---|---|
| `none` | 0~6일 | **지표를 만들지 않는다**(null 반환) |
| `low` | 7~13일 | 주중/주말 한 바퀴 — 사실만, 예측 없음 |
| `medium` | 14~29일 | 짧은 추세가 보임 — 예측 허용 |
| `high` | 30일+ | 회전 빈도를 말할 수 있는 최소치 |

### 예측(`estimatedWaitDays`)을 내는 조건 — 전부 충족해야 한다

1. 신뢰도 `medium` 이상(14일+)
2. 지금 대기 인원 > 0
3. `waitPerDay >= 0.05` (실제로 줄고 있고, 잡음 수준이 아님)

셋 중 하나라도 아니면 `null`이고 화면에 예측 문장이 나오지 않는다.

## 4. 하면 안 되는 것

1. **신뢰도 임계를 낮추지 말 것.** 3~4일치로 "회전율"을 말하면 공공데이터의 갱신
   지연(파일이 며칠 그대로인 날이 있다 — 2026-08-03에 변동 5건뿐이었다)을 추세로
   착각해 보호자를 오도한다.
2. **예측을 단정형으로 쓰지 말 것.** "약 N일 걸릴 것으로 보여요"까지가 선이다.
   "N일 뒤 입소 가능"은 우리가 보증할 수 없는 말이다.
3. **입소 가능 여부를 확답하지 말 것.** 화면에 항상 "실제 입소 가능 여부는 시설에
   직접 확인" 안내를 유지한다. 공단 공개값과 시설의 실제 사정은 다를 수 있다.
4. **이 지표를 팔지 말 것.** 신뢰 데이터를 돈 받고 바꾸지 않는다는 원칙(2026-08-06
   사용자 방침)이 여기에도 적용된다. B2B에 "귀 시설 회전율" 같은 **자기 시설 리포트**를
   제공하는 것은 되지만, 노출 순위를 이 값으로 팔지는 않는다.

## 5. 앞으로 (데이터가 쌓이면)

| 시점 | 가능해지는 것 |
|---|---|
| 관측 30일 | 회전 빈도("월 평균 N번 자리가 남")를 시설 비교 축으로 |
| 관측 90일 | 계절성(연말·명절 전후 회전 변화) |
| 관측 180일 | 지역별 "평균 대기 기간" 벤치마크 — 지역 페이지 콘텐츠로 |

⚠️ 어느 단계든 **표본이 얇은 시설은 지표를 만들지 않는다**는 원칙은 유지한다.
비교 축으로 쓸 때는 "관측 N일 이상인 시설끼리만" 비교해야 공정하다.
