## 1. 왜 이렇게 설계했나 — 지켜야 할 선

보호자와 매니저가 구두 합의만으로 진행하다 분쟁이 나는 걸 막되, **플랫폼이 계약
당사자가 되지 않는 선**을 지킨다.

| 하는 것 | 하지 않는 것 |
|---|---|
| 표준 양식 제공 | 계약 체결·중개 |
| 서명 사실 기록·보관 | 사례비 결정·지급·정산 |
| 사본을 양측에 발송 | 상대방 신원·자격 보증 |
| 위변조 방지(해시) | 이행 감독·분쟁 개입 |

이 원칙은 이용약관 제12조·매니저 약관과 같은 입장이며, 합의서 본문 제1조·제2조에도
그대로 박혀 있다. **조항을 수정할 때 이 문구들이 흐려지지 않게 할 것.**

> 조항은 참고용 표준 문안이지 법률 자문이 아니다. 서비스 확대 전 변호사 검토 필요.

> ℹ️ 2026-08-05 — `content.terms`의 사례비(payAmount·payUnit)는 이제 **확정된 지원의
> 제안 금액(`CareRequestApplication.proposedAmount`)이 있으면 그 값을** 기록하고,
> 없으면 기존대로 요청의 희망가를 기록한다(역경매 도입). §1의 선은 그대로다 —
> 회사는 두 당사자가 정한 값을 "기록"할 뿐, 금액 결정에 개입하지 않는다.
> 오히려 보호자 희망가만 적던 예전보다 실제 합의에 가까운 기록이 됐다.

## 2. 데이터 구조

`CareAgreement` (prisma/schema.prisma)

| 필드 | 용도 |
|---|---|
| `careRequestId` (unique) | 돌봄 요청 1건당 합의서 1건 |
| `content` (jsonb) | **서명 시점의 합의 내용 전문** — 당사자·기간·업무범위·조항 전문 |
| `contentHash` | content 정규화 문자열의 SHA-256 |
| `guardian*` / `sitter*` | 이름, 서명 이미지(dataURL), 서명 시각, 접속 IP, 기기 정보, 이메일 |
| `copySentAt` | 양측 서명 완료 후 사본 발송 시각 |

**관계(@relation)를 일부러 걸지 않았다.** User·CareRequest에 Cascade로 묶으면 한쪽이
탈퇴하는 순간 합의서가 사라져 **남은 당사자가 권리를 증명할 자료를 잃는다.**
content에 전문이 들어 있어 원본 요청이 없어져도 문서는 온전하다.

## 3. 위변조 방지

1. 첫 서명 시점에 합의 내용을 `content`에 **통째로 봉인**한다(이후 원본 요청이 바뀌어도 불변)
2. 정규화 JSON(`stableStringify` — 키 순서 무관)의 SHA-256을 `contentHash`에 저장
3. 조회할 때마다 해시를 재계산해 대조 → 불일치면 화면에 경고(`hashValid: false`)

해싱은 **서버 전용** `lib/careAgreementHash.ts`에 둔다. `lib/careAgreement.ts`(클라이언트도
import)에 `node:crypto`를 두면 합의서 화면 번들에 폴리필이 딸려와 **236KB로 부푼다**(실측).

## 4. 서명 증거

전자서명은 "누가 서명했는가"를 다투게 되므로 정황을 함께 남긴다:
로그인 계정(이메일) + 입력한 이름 + 손글씨 서명 + **서버 시각** + 접속 IP + 기기 정보.

- IP는 `x-forwarded-for` 첫 값(프록시 경유)
- 서명 이미지는 PNG dataURL, 400KB 초과 시 거부
- **이미 서명한 쪽의 재서명은 409로 차단** — 서명 시각이 덮어써지면 기록의 의미가 없다

## 5. 흐름

```
매칭 확정(MATCHED)
  → 양쪽 화면에 "합의서 확인·서명" 진입점
  → GET /api/care-agreement : 저장본이 있으면 그것, 없으면 초안(저장 안 함)
  → PATCH : 본인 몫 서명. 첫 서명 시 content 봉인 + 해시 생성
  → 양측 서명 완료 → 각자 이메일로 사본 발송(따로 보내 주소 노출 방지)
```

초안을 미리 저장하지 않는 이유: 서명 전에는 요청 내용이 바뀔 수 있어 초안도 따라
바뀌어야 하기 때문. 서명하는 순간이 곧 봉인 시점이다.

**조회 조건**: 보호자는 자기 요청(MATCHED·COMPLETED) + 확정된 지원,
매니저는 자기 지원(매칭확정·돌봄완료). 취소된 건(CANCELLED)은 조회되지 않는다.

## 6. 양식 버전

`AGREEMENT_VERSION` — 조항을 바꾸면 올린다. 이미 서명된 합의서는 `content`에 그때
조항 전문을 품고 있어 **소급되지 않는다.**

| 버전 | 변경 |
|---|---|
| 1.0 | 최초 (제1조 목적·당사자 ~ 제9조 분쟁해결) |
| 1.1 | 제2조 (회사의 지위와 책임 범위) 신설 — 고용관계 부인, 금전 미관여, 신원 미보증, 사고 무책임, 보험 권고. 이하 조항 번호 1씩 밀림 |

## 7. PDF

서버 PDF 생성은 하지 않는다 — 한글 폰트 임베딩으로 함수가 무거워지고(수 MB) 서버리스
크기 제한에 걸린다. 대신 **브라우저 인쇄 → "PDF로 저장"** 경로를 안내한다
(양측 서명 완료 시에만 인쇄 버튼 노출, `@media print`로 입력 영역·버튼은 감춤).

## 8. 아직 안 된 것

- **이메일 실제 발송**: 코드는 완성됐으나 발신 주소가 `onboarding@resend.dev`(Resend
  테스트 전용)라 실제로는 거부될 가능성이 크다. 정식 도메인 인증 후 교체 필요
- **본인확인 강화**: 지금 신원 근거는 카카오 로그인 계정뿐. 분쟁 시 입증력을 높이려면
  휴대폰 본인인증이 필요하나, 그 경우 직업소개사업 등록 검토가 함께 따라온다(§1)
- **서명 후 취소 처리**: 합의서에 서명한 뒤 보호자가 요청을 취소하면 합의서는 DB에
  남지만 화면에서 조회되지 않는다. 분쟁 상황이므로 별도 흐름이 필요하다
