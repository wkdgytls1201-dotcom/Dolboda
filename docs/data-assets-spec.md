# 데이터 자산 — 무엇을 쌓고, 어디에 쓰고, 무엇을 팔지 않는가

> 최초 작성: 2026-08-06 (전수 조사 실측 기준)
>
> **새 지표·리포트를 만들기 전에 §0(원칙)과 §5(팔지 않는 것)를 먼저 읽을 것.**
> 관련 문서: [vacancy-insight-spec](vacancy-insight-spec.md)(자리 인사이트 상세),
> [business-console-spec](business-console-spec.md)(B2B 콘솔),

## 0. 원칙 — 이 문서 전체에 적용된다

1. **시간이 만드는 자산에 집중한다.** 공공데이터를 예쁘게 보여주는 건 누구나 따라
   한다. 우리만 가진 건 **매일 저장해야만 생기는 변화**다. 오늘 시작한 경쟁자는
   우리보다 항상 뒤에 있다.
2. **표본이 얇으면 지표를 만들지 않는다.** null을 돌려주고 화면에서 섹션을 감춘다.
   "비교 불가"를 "차이 없음"처럼 보이게 하는 것이 가장 흔한 거짓말이다.
3. **관측된 사실과 추정을 문장에서 구분한다.** 추정에는 근거 기간과 "추정" 표시를
   반드시 붙인다.
4. **오염값을 먼저 거른다.** 공단 원본에 "월 1원", "현원 > 정원", 주소 결손(37곳)이
   섞여 있다. 기준값·평균을 만들 때 이걸 안 빼면 지표 전체가 오염된다.
5. **신뢰 데이터는 팔지 않는다**(2026-08-06 사용자 방침). §5 참고.

## 1. 자리 시계열 — `FacilitySnapshot` ★ 최우선 자산

| 항목 | 값(2026-08-06 실측) |
|---|---|
| 규모 | 28,504행 / 27,493개 시설 |
| 시작 | 2026-08-02(전체 기준선) |
| 일일 증가 | 289~394행(변동분만 적재) |
| 이력 2일+ 보유 | 705곳 |

**왜 자산인가**: 공단은 오늘 값만 공개한다. "자리가 잘 나나", "대기 얼마나 기다리나"는
공개 데이터만으로 누구도 답할 수 없다.

**어디에 쓰는가**
- 시설 상세 "자리 추이" 막대 + 인사이트 문장 (`app/facility/[id]/VacancyTrend.tsx`)
- 계산: `lib/vacancyTrend.ts`(시계열 forward-fill) · `lib/vacancyInsight.ts`(지표)

**주의**: 적재가 듬성듬성하다(바뀐 시설만). forward-fill 없이 원본 행을 그리면
그래프가 실제와 반대로 보인다. 상세는 [vacancy-insight-spec](vacancy-insight-spec.md).

**앞으로**: 30일 → 회전 빈도 비교축 · 90일 → 계절성 · 180일 → 지역별 대기 벤치마크.

## 2. 비급여 비용 기준값 — `lib/feeBenchmarks.generated.ts`

| 항목 | 값 |
|---|---|
| 규모 | 시도 17 × 유형 2 × 항목 4 = 기준값 109개 (9KB) |
| 생성 | `scripts/build-fee-benchmarks.mjs` |
| 표본 하한 | 항목당 10곳 · 월 1만원 초과분만 |
| 통계량 | **중앙값**(평균 아님 — 상급침실료 극단값이 평균을 끌어올린다) |

**왜 생성 파일인가**: 페이지가 매번 집계하면 경기도 기준 1.2초(실측). 28,000여
상세페이지가 각자 그럴 수 없다. 비급여 비용은 **일일 동기화 대상이 아니라** 기관
마스터를 다시 임포트할 때만 바뀌므로 미리 구워도 어긋나지 않는다.

> ⚠️ **기관 상세정보 마스터를 다시 임포트하면 이 스크립트도 다시 돌릴 것.**
> `node --env-file=.env.local scripts/build-fee-benchmarks.mjs`

**어디에 쓰는가**
- 보호자: 시설 상세 비급여 항목마다 "평균보다 N% 높아요" (`components/FeeCompareBar.tsx`)
- 시설(B2B): 월간 보고서 "비급여 비용 · 지역 비교" (`lib/monthlyReport.ts`의 `fees`)

**알려진 한계**: 공단 원본이 병실 등급을 구분하지 않아 "상급침실사용료"가 한 시설에
1인실·2인실로 두 번 올 수 있다(실측 155,000원·310,000원). 기준값은 이름 단위라 두 행이
같은 값과 비교된다 — 지금은 여기까지가 정확한 한계다.

## 3. 수요 신호 — `FacilityDailyView` · `ConsultRequest` · `AdEvent`

| 자산 | 규모(실측) | 상태 |
|---|---|---|
| `FacilityDailyView` | 315회 / 77곳 | ✅ 적재 중 (`/api/facilities/view` 비컨) |
| `ConsultRequest` | 3건 | ✅ |
| `AdEvent` | 0행 | ✅ 파이프라인 정상 — **스폰서 계약이 0건**이라 광고가 안 그려질 뿐 |
| `FacilityFavorite` | 7건 | ✅ |
| `RegionInterest` | 0건 | ⚠️ 기능은 있는데 등록자 0 — 발견되지 않는다는 UX 신호 |

**설계**: 이벤트를 행마다 쌓지 않고 (시설, 날짜) 하나로 뭉쳐 카운터만 올린다.
개인 식별 정보는 저장하지 않는다.

**어디에 쓰는가**: B2B 콘솔·월간 보고서. 이번 세션에 **조회→상담 전환율**을 추가했다
(`consults.conversionPct`) — 조회 30회 미만이면 null(한 건이 수치를 흔든다).
"노출을 늘릴 문제인가, 페이지를 손볼 문제인가"를 가르는 지표라 판매 대화의 근거가 된다.

## 4. 돌봄 기록 — `CareLog` · `CareQuickNote`

**어디에 쓰는가**: 매니저 공개 프로필·지원자 카드의 실적(완료 건수·평점·기록일 수·
반응 횟수) + **반응 종류별 분포**(이번 세션 추가).

> ★ **반응 분포는 "우리가 매긴 점수"가 아니라 "보호자가 누른 버튼의 집계"다.**
> 매니저 법적 거리 방침(2026-08-06)상 회사가 매니저를 평가·채근하는 지표를 만들면
> 안 된다. 그래서 "기록률 92%" 같은 성실도 점수는 **의도적으로 만들지 않았다** —
> 그건 평가로 읽힌다. 0인 반응 종류를 숨기는 것도 같은 이유다(없는 것을 강조하면
> 그게 곧 감점처럼 읽힌다).

## 5. 팔지 않는 것 — 선

| 팔아도 되는 것 | 팔지 않는 것 |
|---|---|
| **노출 위치**(스폰서 슬롯·배너) — 광고임을 표시 | **신뢰 데이터 자체**(평가등급·안심지수·후기·자리 추이 수치) |
| 시설 **자기 데이터** 리포트(조회수·전환율·자기 비용의 지역 대비) | 다른 시설을 불리하게 보이게 하는 비교 |
| ⭐ 돌봄 스타 — 지원자 목록 **상단 노출**(2026-08-06 사용자 확정) | 매니저의 실적·후기 숫자를 바꾸는 것 |

**근거**: 광고는 표시광고법상 광고임을 알 수 있으면 되고, 신뢰 데이터를 돈으로
바꾸면 서비스의 존재 이유가 사라진다. 별(⭐)이 상단에 오는 것은 허용하되 **그 안의
숫자는 건드리지 않는다**.
