# 돌봄일지 기획서

> 최종 갱신: 2026-08-03 · 상태: **설계 단계 (미구현)**
> 선행 조건: 매칭이 실제로 돌아야 함 (2026-08-03 기준 합의서 0건 · 매칭확정 0건)

---

## 0. 한 줄 정의

**돌봄일지는 매니저가 남기고 보호자가 보는, 그날의 돌봄 기록이다.**
목적은 두 가지 — 보호자가 매일 앱을 열 이유를 만들고, 매니저의 성실함이 증거로 남게 하는 것.

---

## 1. 왜 만드는가

### 1-1. 지금 매칭 이후에 앱을 열 이유가 없다

현재 돌봄 흐름은 `요청 등록 → 매니저 지원 → 확정 → 합의서 서명`에서 **끝난다.**
그 다음부터 실제 돌봄은 몇 주~몇 달 이어지는데 그 기간 동안 플랫폼은 아무 역할이 없다.

보호자는 앱을 떠나고, 매니저와 보호자는 전화·카톡으로 옮겨간다. 다음 돌봄이 필요할 때
우리를 다시 찾을 이유가 남지 않는다. **이것이 지금 가장 큰 리텐션 구멍이다.**

### 1-2. 보호자의 진짜 불안은 "매칭 후"에 있다

시설·매니저를 고르는 건 며칠이면 끝난다. 하지만 그 뒤로 몇 달간 이어지는
**"오늘 우리 어머니 괜찮으셨나"**는 매일 새로 생기는 불안이다.
멀리 사는 자녀일수록 크고, 확인할 방법이 전화밖에 없다.

### 1-3. 매니저에게도 필요하다

- 성실하게 일해도 **증명할 방법이 없다.** 기록이 쌓이면 그게 곧 경력이다
- "제대로 안 했다"는 분쟁에서 **자기를 방어할 자료**가 된다
- 돌보다 안에서 평판이 쌓이면 다음 일자리를 얻기 쉬워진다 → 매니저 리텐션

## 2. 경쟁사 조사 (2026-08-03)

### 2-1. 케어네이션 — 일지가 **정산의 근거**

가족간병 서비스에서 간병일지를 **매일 당일 작성**하게 하고, 그 기록이 월말 간병비 청구의
기초가 된다. 앱에서 '간병비 청구' → 3~5일 심사 → 승인 후 2~3일 내 입금.

**출석 증명이 강제된다** — GPS 기반 위치 확인 매일 실시, QR코드 스캔 또는 사진 촬영.

기록 항목: 간병 시간 / 식사 보조 / 투약 관리 / 활동 보조.
"간병함"처럼 뭉뚱그린 기록은 반려되고 구체적 서술을 요구한다.

### 2-2. 케어닥 — 케어코디 정보 투명화 중심

보호자가 앱에서 케어코디의 **사진·경력·돌봄 이력**을 확인할 수 있게 해 신뢰도를 확보하는
방향. 신청→매칭→결제를 앱 하나로 처리한다.

### 2-3. 전용 앱들도 있다

`케어로그 — 어르신 돌봄 모니터링`, `케어로 — 요양 중인 가족의 하루를 한눈에` 등
**돌봄 모니터링만 하는 앱이 따로 존재한다.** 이 수요가 독립 앱이 나올 만큼 크다는 뜻이다.

### 2-4. 여기서 배울 것과 **베끼면 안 되는 것**

| 배울 것 | 이유 |
|---|---|
| 매일 당일 작성 원칙 | 몰아 쓰면 기록의 신뢰가 무너진다 |
| 구체적 서술 강제 | "간병함" 한 줄은 아무 정보가 없다 |
| 항목 구조화(식사·투약·활동) | 자유서술만 두면 매니저마다 품질이 갈린다 |

| ❌ 베끼면 안 되는 것 | 이유 |
|---|---|
| **일지 = 정산 근거 구조** | 우리는 사례비 지급·정산에 관여하지 않는다(§3) |
| **GPS·QR 출석 강제** | 근태 감독이 되어 사용자성 판단 위험이 커진다(§3) |

## 3. ⚠️ 지켜야 할 법적 선 (가장 중요)

[docs/care-agreement-spec.md §1](care-agreement-spec.md)의 원칙이 그대로 적용된다.

| 하는 것 | 하지 않는 것 |
|---|---|
| 기록할 **양식**을 제공 | 기록의 **사실 여부를 보증** |
| 기록을 **보관·전달** | **정산 근거**로 사용 |
| 양측이 함께 보게 함 | **근태 감독**(GPS·출퇴근 강제) |

### 왜 이 선인가

1. **정산에 쓰면 계약 당사자가 된다.** 케어네이션은 일지를 근거로 간병비를 심사·지급한다.
   그 순간 플랫폼이 대금 지급 주체가 된다 — 우리 약관 제12조와 정면 충돌하고,
   직업안정법상 유료직업소개사업 등록 문제로 이어진다.
   **돌보다에서 사례비는 두 당사자가 직접 정하고 직접 주고받는다.**

2. **GPS 출퇴근을 강제하면 근태 감독이 된다.** 플랫폼이 근무 시간을 관리·검증하면
   매니저를 사실상 지휘·감독하는 모양이 되고, 근로자성 분쟁의 재료가 된다.
   → **위치 기록은 넣지 않는다.** 작성 시각(서버 시각)만 남긴다.

3. **일지는 증거이지 판정이 아니다.** 우리는 "이 매니저가 잘했다/못했다"를 판단하지 않는다.
   기록을 그대로 보관하고 양측에 보여줄 뿐이다. 화면에도 이 사실을 밝힌다.

> **화면 문구 원칙**: "돌보다는 기록을 보관·전달할 뿐, 내용의 사실 여부를 확인하거나
> 보증하지 않아요. 사례비 정산은 두 분이 직접 하세요."

## 4. 신뢰를 만드는 설계 — 이게 핵심이다

일지는 **"매니저가 썼다"는 것만으로는 신뢰가 안 생긴다.** 마음만 먹으면 지어낼 수 있기
때문이다. 그렇다고 GPS로 감시하면 법적 선을 넘는다. 그 사이에서 신뢰를 만드는 방법:

### 4-1. 사후 수정 불가 (append-only)

작성한 일지는 **수정·삭제할 수 없다.** 오탈자를 고치려면 "정정 기록"을 새로 추가하고,
원본과 정정본이 나란히 보인다. 합의서의 위변조 방지와 같은 사상이다.

→ 나중에 말을 바꿀 수 없으니 기록 자체의 무게가 생긴다.

### 4-2. 작성 시각은 서버가 찍는다

매니저가 날짜를 고를 수 없다. **서버 시각으로 기록되고, 며칠 뒤에 쓰면 "3일 늦게 작성됨"이
그대로 표시된다.** 늦게 쓰는 걸 막지는 않되(현장 사정이 있다), 숨기지도 않는다.

### 4-3. 사진은 "그날 찍은 것"만

- 카메라 촬영만 허용하고 **갤러리 업로드는 막는다**(EXIF 촬영시각 검증 + capture 속성)
- 사진은 **선택**이다. 강제하면 어르신 프라이버시 침해가 되고, 못 찍는 상황이 많다

### 4-4. 보호자가 읽었는지 매니저도 안다

보호자가 일지를 열면 매니저 쪽에 "보호자가 확인했어요"가 뜬다.
→ 매니저는 자기 기록이 읽힌다는 걸 알고, 보호자는 무응답이 아니라는 걸 안다.
**양방향이라야 관계가 유지된다.**

### 4-5. 빈 날은 빈 날로 보여준다

일지를 안 쓴 날은 채우지 않고 비워둔다. "작성된 기록 없음"이 그대로 보인다.
→ 없는 데이터를 있는 것처럼 만들지 않는다는 프로젝트 원칙 그대로.

## 5. 무엇을 기록하는가

**설계 원칙: 매니저가 1~2분 안에 끝낼 수 있어야 한다.** 길면 아예 안 쓴다.

### 5-1. 기본 기록 (탭 몇 번으로 끝)

| 항목 | 입력 방식 | 비고 |
|---|---|---|
| 식사 | 아침/점심/저녁 × (다 드심·조금·거의 못 드심) | 3탭 |
| 수면 | 잘 주무심 / 뒤척이심 / 거의 못 주무심 | 1탭 |
| 배변 | 정상 / 변비 / 설사 / 실금 | 1탭 |
| 기분·상태 | 좋으심 / 보통 / 힘들어하심 | 1탭 |
| 투약 | 복용함 / 거르심 / 해당 없음 | 1탭 |

### 5-2. 오늘 한 일 (선택 칩)

돌봄 요청에 적힌 업무 범위에서 자동 생성된 칩을 탭.
예: `세면 도움` `식사 보조` `산책` `병원 동행` `말벗`

### 5-3. 한 줄 메모 (선택, 자유서술)

"오늘은 옛날 이야기를 오래 하셨어요" 같은 것. **이게 보호자가 가장 좋아하는 부분**이다.
숫자보다 이런 한 줄이 안심을 준다.

### 5-4. 특이사항 (선택, 눈에 띄게)

낙상·발열·평소와 다른 점. 이건 별도 색으로 강조되고 **보호자에게 즉시 알림**이 간다.

## 6. 데이터 모델 (초안)

```prisma
// 돌봄일지 — 매니저가 남기고 보호자가 보는 하루 기록.
//
// ⚠️ 이 기록은 정산 근거가 아니다. 돌보다는 기록을 보관·전달만 하며 사실 여부를
// 보증하지 않는다(docs/care-agreement-spec.md §1과 같은 선).
// 위치(GPS)는 수집하지 않는다 — 근태 감독이 되면 근로자성 분쟁의 재료가 된다.
model CareLog {
  id            String @id @default(cuid())
  careRequestId String
  // 누가 썼는지 — 매칭된 매니저
  sitterProfileId String

  // 돌봄이 이루어진 날 (YYYY-MM-DD, KST). 매니저가 고르되 미래 날짜는 막는다.
  careDate      String
  // 실제로 기록한 시각 — 서버가 찍는다. careDate와 차이가 크면 화면에 "N일 늦게 작성"
  createdAt     DateTime @default(now())

  // 구간값 (자유 입력 아님 — 화면 선택지와 1:1)
  mealBreakfast String?  // "다 드심" | "조금" | "거의 못 드심" | null
  mealLunch     String?
  mealDinner    String?
  sleep         String?
  bowel         String?
  mood          String?
  medication    String?

  tasks         String[] // 오늘 한 일 칩
  memo          String?  // 한 줄 메모
  // 특이사항 — 값이 있으면 보호자에게 즉시 알림
  alertNote     String?

  photos        Json?    // [{url, takenAt}] — 카메라 촬영만

  // 보호자가 읽은 시각 (매니저에게 "확인했어요"로 표시)
  readAt        DateTime?

  // 정정 기록 — 원본을 고치지 않고 새 행을 만들어 잇는다(append-only)
  correctsId    String?

  @@index([careRequestId, careDate])
  @@index([sitterProfileId])
}
```

**민감정보 주의**: 식사·배변·투약은 건강정보다. `CareProfile`과 같은 수준으로 다루고
개인정보처리방침 수집 항목에 반영해야 한다. 돌봄 종료 후 보관 기간도 정해야 한다.

## 7. 화면 구성

### 7-1. 매니저 — 작성 (`/mypage/sitter/log/[careRequestId]`)

- 오늘 날짜가 기본, 큰 버튼 위주(현장에서 한 손으로 쓴다)
- **저장 버튼 하나** — 항목을 다 안 채워도 저장된다(완벽을 요구하면 안 쓴다)
- 이미 쓴 날은 "작성 완료"로 잠기고, 고치려면 "정정 기록 남기기"

### 7-2. 보호자 — 열람 (`/mypage/care-log/[careRequestId]`)

- **달력 뷰**가 기본 — 쓴 날/안 쓴 날이 한눈에 보인다
- 날짜를 누르면 그날 기록. 사진이 있으면 크게
- 특이사항이 있는 날은 달력에서부터 다른 색
- 주간 요약: "이번 주 식사 잘하신 날 5일 / 특이사항 1건"

### 7-3. 알림 연동

특이사항 작성 시 보호자에게 즉시 알림 → [찜 알림 인프라](favorite-alert-spec.md)와 같은 발송 경로를 쓴다.
**이 기능이 알림 인프라를 필요로 하는 두 번째 이유다.**

## 8. 사업모델 연결

돌보다의 현재 수익은 전부 B2B(시설 광고·구독)다. 돌봄일지는 **첫 B2C 유료화 후보**다.

| 후보 | 내용 | 검토 필요 |
|---|---|---|
| 기록 보관 연장 | 기본 3개월 무료, 그 이상 보관은 유료 | 거부감 적음 |
| PDF 리포트 | 월간 돌봄 리포트 PDF (요양병원 제출·가족 공유용) | 실수요 있음 |
| 가족 공유 | 형제자매 여러 명이 같이 보기 | 계정 구조 변경 필요 |

⚠️ **일지 작성 자체를 유료화하면 안 된다.** 안 쓰게 되고 그러면 기능이 죽는다.
유료화는 "쌓인 기록을 더 쓰는 방법"에만 건다.

## 10. 열어둔 결정

1. **사진 저장 위치** — Supabase Storage 사용 시 용량·비용 추정 필요
2. **보관 기간** — 돌봄 종료 후 몇 개월까지? (합의서는 3년)
3. **가족 공유** — 형제자매 열람 허용 여부 (계정 구조에 영향)
4. **특이사항 알림 강도** — 즉시 푸시 vs 하루 모아서
5. **매니저가 안 쓸 때** — 독려할지 방치할지. 강제하면 형식적 기록만 쌓인다
