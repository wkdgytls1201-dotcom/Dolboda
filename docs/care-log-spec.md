## 0. 한 줄 정의

**돌봄일지는 매니저와 보호자가 서로 확인하는 그날의 돌봄 기록이다.**

성격을 분명히 해둔다 — 이건 **매니저↔보호자 간의 확인 일지**다.
매니저는 오늘 무엇을 했는지 남기고, 보호자는 그걸 보고 확인한다.
"오늘 어머니 괜찮으셨나"에 답하는 것이 이 기능의 전부다.

목적은 두 가지 — 보호자가 매일 앱을 열 이유를 만들고, 매니저의 성실함이 기록으로 남게 하는 것.

---

## 1. 왜 만드는가

### 1-1. 지금 매칭 이후에 앱을 열 이유가 없다

현재 돌봄 흐름은 `요청 등록 → 매니저 지원 → 확정 → 합의서 서명`에서 **끝난다.**
그 다음부터 실제 돌봄은 몇 주~몇 달 이어지는데 그 기간 동안 플랫폼은 아무 역할이 없다.

보호자는 앱을 떠나고, 매니저와 보호자는 전화·카톡으로 옮겨간다. 다음 돌봄이 필요할 때
우리를 다시 찾을 이유가 남지 않는다. **이것이 지금 가장 큰 리텐션 구멍이다.**

### 1-2. 보호자의 진짜 불안은 "매칭 후"에 있다

시설·매니저를 고르는 건 며칠이면 끝난다. 하지만 그 뒤로 몇 달간 이어지는
**"오늘 우리 어머니 괜찮으셨나"**는 매일 새로 생기는 불안이다.
멀리 사는 자녀일수록 크고, 확인할 방법이 전화밖에 없다.

### 1-3. 매니저에게도 필요하다

- 성실하게 일해도 **증명할 방법이 없다.** 기록이 쌓이면 그게 곧 경력이다
- "제대로 안 했다"는 분쟁에서 **자기를 방어할 자료**가 된다
- 돌보다 안에서 평판이 쌓이면 다음 일자리를 얻기 쉬워진다 → 매니저 리텐션

## 2. 경쟁사 조사 (2026-08-03)

### 2-1. 케어네이션 — 일지가 **정산의 근거**

가족간병 서비스에서 간병일지를 **매일 당일 작성**하게 하고, 그 기록이 월말 간병비 청구의
기초가 된다. 앱에서 '간병비 청구' → 3~5일 심사 → 승인 후 2~3일 내 입금.

**출석 증명이 강제된다** — GPS 기반 위치 확인 매일 실시, QR코드 스캔 또는 사진 촬영.

기록 항목: 간병 시간 / 식사 보조 / 투약 관리 / 활동 보조.
"간병함"처럼 뭉뚱그린 기록은 반려되고 구체적 서술을 요구한다.

### 2-2. 케어닥 — 케어코디 정보 투명화 중심

보호자가 앱에서 케어코디의 **사진·경력·돌봄 이력**을 확인할 수 있게 해 신뢰도를 확보하는
방향. 신청→매칭→결제를 앱 하나로 처리한다.

### 2-3. 전용 앱들도 있다

`케어로그 — 어르신 돌봄 모니터링`, `케어로 — 요양 중인 가족의 하루를 한눈에` 등
**돌봄 모니터링만 하는 앱이 따로 존재한다.** 이 수요가 독립 앱이 나올 만큼 크다는 뜻이다.

### 2-4. 케어네이션 간병일지 상세 (조사 결과)

**시간대 3분할 구조**를 쓴다. 이게 핵심 골격이다.

| 시간대 | 기록 내용 |
|---|---|
| 오전 | 기상 도움, 세면, 아침 식사 및 복약 관리 |
| 오후 | 점심 식사, 휴식 관리, 필요시 병원 동행 |
| 저녁 | 저녁 식사, 개인위생 관리, 취침 준비 |

**항목별 기입 규칙** (구체성을 강하게 요구한다)

| 항목 | 기입 예시 | 주의사항 |
|---|---|---|
| 간병 시간 | 오전 9시 – 오후 6시 | 정확한 시간 기록 |
| 식사 보조 | 아침 죽 반 공기, 점심 일반식 | 식단 변화 세부 기록 |
| 투약 관리 | 오전 9시 고혈압약 복용 | 시간과 약물명 정확히 |
| 활동 보조 | 오후 2시 병원 동행 | 외출 시 동행 여부 명시 |

**운영 원칙**: 매일 당일 작성. "간병함"처럼 뭉뚱그린 기록은 부적절한 예로 명시.
출석은 GPS 위치 확인 + 간병 시작 시 체크인 필수, QR 스캔 또는 사진 촬영.

### 2-5. 우리가 가져올 것

**골격은 대부분 가져온다.** 시간대 3분할, 항목 구조화, 매일 당일 작성, 구체적 기입 유도.
이미 검증된 형식이라 새로 발명할 이유가 없다.

**바꾸는 것은 워딩과 UX/UI다.**

| 케어네이션 | 돌보다 |
|---|---|
| "간병일지" | **"돌봄일지"** — 간병보다 넓은 돌봄 전반을 다룬다 |
| "간병인" | **"돌보다 매니저"** |
| 자유서술 위주(타이핑 부담) | **탭 선택 + 한 줄 메모** — 1~2분 안에 끝나게(§5) |
| 정산 서류 톤 | **가족에게 전하는 안부 톤** — "오늘 어머니는요" |

자유서술을 탭 선택으로 바꾸는 게 가장 큰 차이다. 케어네이션은 정산 근거라 상세 서술이
필수지만, 우리 일지는 **확인용**이라 매니저가 부담 없이 매일 쓰는 게 더 중요하다.
길면 안 쓰고, 안 쓰면 기능이 죽는다.

## 3. 범위 — 1단계는 "확인 일지"까지

### 3-1. 1단계 범위 (지금 만들 것)

돌봄일지 1단계는 **매니저↔보호자 확인 일지**다. 정산·근태와 엮지 않는다.

| 1단계에서 하는 것 | 1단계에서 안 하는 것 |
|---|---|
| 기록 양식 제공 | 기록의 사실 여부 판정 |
| 기록 보관·전달 | 정산 자동 계산 |
| 양측이 함께 확인 | 출퇴근 검증 |

**이유는 법이 아니라 순서다.** 지금은 매칭이 0건이라 정산·근태 기능을 붙일 대상 자체가
없다. 확인 일지만으로도 리텐션 효과는 나오고, 이게 돌아가야 그 위에 다음 단계를 얹을 수 있다.

### 3-2. 2단계 후보 (플랫폼이 커지면 검토) 🔖

사업이 커지면 아래를 하게 될 수 있다. **지금 못박아 배제하지 않고 열어둔다.**
다만 각각 **착수 전에 반드시 확인해야 할 것**이 있어 여기 남긴다.

| 후보 | 무엇 | 착수 전 확인할 것 |
|---|---|---|
| **정산 연동** | 일지를 근거로 사례비 자동 계산·청구 (케어네이션 방식) | 플랫폼이 대금 지급 주체가 되면 **직업안정법상 유료직업소개사업 등록**이 필요할 수 있다. 이용약관 제12조·[합의서 조항](care-agreement-spec.md) 개정도 함께 가야 한다. **변호사 검토 선행 권장** |
| **GPS·QR 출퇴근** | 체크인·체크아웃 위치 검증 | 플랫폼이 근무 시간을 관리·검증하면 매니저 **근로자성 분쟁**의 재료가 될 수 있다. 매니저 약관에 위탁관계를 명확히 하는 조항 정비 필요 |
| **에스크로 결제** | 보호자 선결제 → 완료 후 매니저 지급 | 전자금융거래법상 **선불전자지급수단** 해당 여부 검토 필요 |

> 이 세 가지는 케어네이션이 이미 하고 있다. 즉 **불가능한 게 아니라 준비가 필요한 것**이다.
> 우리도 규모가 되면 같은 길을 갈 수 있고, 그때 이 표를 체크리스트로 쓴다.

### 3-3. 1단계 화면 문구

1단계에서는 일지가 정산과 무관하므로 화면에도 그대로 밝힌다:

> "이 일지는 두 분이 서로 확인하시는 기록이에요. 사례비 정산과는 별개예요."

정산 연동을 하게 되면 이 문구부터 바꿔야 한다.

## 4. 신뢰를 만드는 설계 — 이게 핵심이다

일지는 **"매니저가 썼다"는 것만으로는 신뢰가 안 생긴다.** 마음만 먹으면 지어낼 수 있기
때문이다.

케어네이션은 GPS·QR 출석 체크로 이걸 푼다. 우리도 언젠가 그 길을 갈 수 있지만(§3-2),
1단계에서는 **위치 수집 없이 기록 자체의 무게로** 신뢰를 만든다. 아래 다섯 가지는
GPS를 붙이더라도 그대로 유효한 장치들이다.

### 4-1. 사후 수정 불가 (append-only)

작성한 일지는 **수정·삭제할 수 없다.** 오탈자를 고치려면 "정정 기록"을 새로 추가하고,
원본과 정정본이 나란히 보인다. 합의서의 위변조 방지와 같은 사상이다.

→ 나중에 말을 바꿀 수 없으니 기록 자체의 무게가 생긴다.

### 4-2. 작성 시각은 서버가 찍는다

매니저가 날짜를 고를 수 없다. **서버 시각으로 기록되고, 며칠 뒤에 쓰면 "3일 늦게 작성됨"이
그대로 표시된다.** 늦게 쓰는 걸 막지는 않되(현장 사정이 있다), 숨기지도 않는다.

### 4-3. 사진은 "그날 찍은 것"만

- 카메라 촬영만 허용하고 **갤러리 업로드는 막는다**(EXIF 촬영시각 검증 + capture 속성)
- 사진은 **선택**이다. 강제하면 어르신 프라이버시 침해가 되고, 못 찍는 상황이 많다

### 4-4. 보호자가 읽었는지 매니저도 안다

보호자가 일지를 열면 매니저 쪽에 "보호자가 확인했어요"가 뜬다.
→ 매니저는 자기 기록이 읽힌다는 걸 알고, 보호자는 무응답이 아니라는 걸 안다.
**양방향이라야 관계가 유지된다.**

### 4-5. 빈 날은 빈 날로 보여준다

일지를 안 쓴 날은 채우지 않고 비워둔다. "작성된 기록 없음"이 그대로 보인다.
→ 없는 데이터를 있는 것처럼 만들지 않는다는 프로젝트 원칙 그대로.

## 5. 무엇을 기록하는가 — **30초 안에 끝나야 한다**

### 5-0. 설계 원칙: 부담 없이, 매일

케어네이션은 정산 근거라 상세 기록이 **필수**다. 반려되면 돈을 못 받으니 매니저가
어쩔 수 없이 쓴다. 우리는 그 강제력이 없다 — **부담스러우면 그냥 안 쓴다.**

> **안 쓰는 완벽한 일지보다, 매일 쓰는 허술한 일지가 낫다.**

그래서 시간대 3분할(오전/오후/저녁 × 항목마다 선택)은 **버린다.** 9번 탭해야 하는 구조는
매일 쓰기엔 무겁다. 대신 **기본 3탭 + 나머지는 전부 선택**으로 간다.

### 5-0-1. ★ 돌봄일지는 의무가 아니다 (양쪽 모두에게)

이 기능의 성격을 화면에서도 분명히 밝힌다. **누구에게도 강제되지 않는다.**

**매니저에게** — 안 써도 불이익이 없다. 돌보다는 일지 작성 여부로 매니저를 평가하거나
제재하지 않는다. 이건 배려이면서 동시에 [법적 포지션](care-agreement-spec.md)이기도 하다 —
플랫폼이 작성을 강제하면 돌봄 이행을 감독하는 모양이 되고, 근로자성 분쟁의 재료가 된다.

**보호자에게** — 매니저에게 일지를 요구할 권리가 생기는 게 아니다. 일지는 매니저가
자발적으로 남기는 것이고, 안 왔다고 해서 돌봄이 부실했다는 뜻이 아니다. 이걸 안 밝히면
"어제 일지 왜 안 썼냐"는 다툼이 플랫폼 안에서 벌어진다.

#### 그럼 매니저가 왜 쓰는가 — 강제 대신 이득으로

강제하지 않는 대신, **쓰면 본인에게 돌아오는 게 있다는 걸 보여준다.**

| 매니저가 얻는 것 | 어떻게 |
|---|---|
| **후기를 더 잘 받는다** | 보호자는 매니저가 뭘 했는지 보여야 후기를 쓸 수 있다. 기록이 없으면 좋게 써주고 싶어도 쓸 말이 없다 |
| **다음 일자리를 구하기 쉬워진다** | 쌓인 기록과 후기가 프로필에 남아 다음 보호자가 고를 때 근거가 된다 |
| **분쟁에서 자기를 지킨다** | "제대로 안 했다"는 말에 대응할 자료가 된다 |
| **경력이 증명된다** | 공백 없이 이어진 기록 자체가 성실함의 증거다 |

**화면 문구 예시** (매니저 작성 화면 하단, 부담 주지 않는 톤으로):

> 일지는 의무가 아니에요. 다만 남겨두시면 보호자님이 어떤 돌봄이었는지 알 수 있어
> 후기를 남기기 쉬워지고, 그 후기가 다음 일자리를 구하실 때 도움이 돼요.

**화면 문구 예시** (보호자 열람 화면, 기록이 없는 날):

> 이 날은 기록이 없어요. 돌봄일지는 매니저님이 자율적으로 남기는 기록이라
> 없는 날도 있을 수 있어요.

#### 후기와 실제로 연결하는 방법

"쓰면 후기를 잘 받는다"가 말뿐이면 매니저가 안 믿는다. **구조로 이어지게 만든다.**
`CareReview`(rating 1~5 + comment)가 이미 있으므로 여기에 붙인다.

| 연결 지점 | 동작 |
|---|---|
| **후기 작성 화면에 일지 요약을 띄운다** | 보호자가 후기를 쓸 때 "이번 돌봄 기간 동안 기록 18일 · 식사 잘하신 날 15일"이 함께 보인다. 쓸 말이 생기고 평가가 후해진다 |
| **매니저 프로필에 성실도 표시** | "돌봄일지 작성률 92%" — 별점과 별개로 성실함이 드러나는 지표. 후기가 아직 없는 신규 매니저에게 특히 유리하다 |
| **돌봄 종료 시 후기 요청 알림** | 일지가 쌓인 돌봄일수록 먼저 요청한다(보호자가 쓸 말이 있으므로 응답률이 높다) |

⚠️ **작성률을 매니저 랭킹이나 노출 순위에 쓰지 않는다.** 그 순간 사실상 강제가 되고,
형식적으로 채우는 기록만 쌓인다. 프로필에 **보여주기만** 한다.

### 5-1. 기본 화면 — 이것만 하면 저장 끝 (3탭 · 약 15초)

큰 이모지 버튼 세 줄. 각 줄에서 하나만 고르면 된다.

| 질문 | 선택지 |
|---|---|
| **식사는 어떠셨어요?** | 🍚 잘 드심 · 🥄 조금 드심 · 😐 거의 못 드심 |
| **컨디션은요?** | 😊 좋으심 · 🙂 평소 같으심 · 😟 힘들어하심 |
| **오늘 하루는?** | ✅ 별일 없었어요 · ⚠️ 알려드릴 일이 있어요 |

세 번째에서 `별일 없었어요`를 고르면 **바로 저장 가능**하다.
`알려드릴 일이 있어요`를 고르면 그때만 특이사항 입력창이 열린다.

**대부분의 날은 여기서 끝난다.** 그게 정상이고, 그래야 매일 쓴다.

### 5-2. 더 남기고 싶을 때만 (접혀 있음)

"＋ 더 자세히 남기기"를 누르면 펼쳐진다. **전부 선택 항목이다.**

| 항목 | 선택지 |
|---|---|
| 수면 | 잘 주무심 / 뒤척이심 / 거의 못 주무심 |
| 배변 | 정상 / 변비 / 설사 / 실금 |
| 복약 | 복용함 / 거르심 / 해당 없음 |
| 오늘 한 일 | 칩 선택 — `세면` `산책` `병원 동행` `말벗` 등 |
| 돌봄 시간 | 시작·종료 시각 |

**칩은 돌봄 요청의 업무 범위에서 자동 생성**한다. 그 돌봄에 없는 항목은 안 보인다
(방문요양인데 "병원 동행" 칩이 뜨면 방해만 된다).

돌봄 시간은 1단계에선 선택이지만, 2단계 정산 연동 시 근거가 되므로 **지금부터 받아둔다**(§3-2).

### 5-3. 오늘 한마디 (선택, 자유서술)

"오늘은 옛날 이야기를 오래 하셨어요" 같은 것. **이게 보호자가 가장 좋아하는 부분**이다.
숫자보다 이런 한 줄이 안심을 준다.

**쓰라고 요구하지 않는다.** 플레이스홀더로 가볍게 권할 뿐:
`가족분께 전하고 싶은 말이 있다면 (선택)`

### 5-4. 사진 (선택)

카메라로 한 장. **강제하지 않는다** — 어르신 프라이버시도 있고, 못 찍는 상황이 많다.

### 5-4-1. 빠른 알림 — 버튼 하나로 그 자리에서 알리기 ⚡

일지와 **별개로** 동작하는 가벼운 기능. 하루가 끝나고 일지를 쓰는 게 아니라,
**그 순간 바로 누르는 것**이다.

돌봄 중에 알릴 일이 생기면 매니저가 버튼 하나만 누른다. 보호자에게 즉시 알림이 간다.

| 버튼 | 보호자에게 가는 알림 |
|---|---|
| 🍚 **식사 하셨어요** | "어머니, 방금 식사하셨어요" |
| 💊 **약 드셨어요** | "어머니, 약 드셨어요" |
| 🚶 **산책 다녀왔어요** | "어머니, 산책 다녀오셨어요" |
| 🏥 **병원 도착했어요** | "어머니, 병원 도착했어요" |
| 😴 **주무세요** | "어머니, 지금 주무세요" |
| ⚠️ **알려드릴 일이 있어요** | 입력창이 열리고, 쓴 내용이 그대로 전달 |

**왜 이게 따로 필요한가**

- 보호자가 가장 불안한 건 "지금" 어떤지다. 저녁에 오는 일지는 그 불안을 못 없앤다
- 매니저에게도 이게 제일 쉽다 — **1탭이면 끝**이고 글을 쓸 필요가 없다
- 누른 기록은 그날 일지에 **자동으로 쌓인다.** 저녁에 따로 일지를 안 써도
  "오늘 식사 2회·복약 1회·산책 1회"가 이미 기록돼 있다

**즉, 빠른 알림을 쓰면 일지가 저절로 채워진다.** 이게 "부담 없이 쓰게 하는" 가장 강한 장치다.

| 항목 | 설계 |
|---|---|
| 버튼 구성 | 돌봄 요청의 업무 범위에서 자동 생성 (병원 동행이 없으면 그 버튼도 없다) |
| 오발송 대응 | 누른 뒤 **1분 안에는 취소 가능** ("잘못 눌렀어요") |
| 연타 방지 | 같은 버튼은 30분에 한 번만 (실수로 여러 번 눌러 보호자를 놀라게 하지 않게) |
| 알림 방식 | 조용한 알림. ⚠️만 강한 알림 |
| 보호자 설정 | 알림 종류별로 끌 수 있다 — 다 받고 싶은 사람도, 특이사항만 받고 싶은 사람도 있다 |

### 5-5. 매니저 부담을 줄이는 장치

| 장치 | 효과 |
|---|---|
| **어제 기록 이어쓰기** | "어제와 같아요" 버튼 한 번이면 어제 값이 채워진다. 대부분의 날은 비슷하다 |
| **저장 조건 없음** | 항목을 하나도 안 골라도 저장된다. 완벽을 요구하면 안 쓴다 |
| **알림은 하루 한 번, 부드럽게** | "오늘 어머니는 어떠셨나요?" 정도. 미작성 독촉은 하지 않는다 |
| **주말·미배정일은 안 물어본다** | 돌봄이 없는 날 알림이 오면 앱이 눈치 없어 보인다 |

## 6. 데이터 모델 (초안)

```prisma
// 돌봄일지 — 매니저와 보호자가 서로 확인하는 하루 기록.
//
// 1단계는 "확인 일지"까지다(정산·근태 미연동, docs/care-log-spec.md §3).
// 2단계에서 정산을 붙이게 되면 workStart/workEnd가 그대로 근거가 되도록 지금부터 받아둔다.
model CareLog {
  id              String @id @default(cuid())
  careRequestId   String
  // 누가 썼는지 — 매칭된 매니저
  sitterProfileId String

  // 돌봄이 이루어진 날 (YYYY-MM-DD, KST). 매니저가 고르되 미래 날짜는 막는다.
  careDate  String
  // 실제로 기록한 시각 — 서버가 찍는다. careDate와 차이가 크면 화면에 "N일 늦게 작성"
  createdAt DateTime @default(now())

  // --- 기본 3탭 (이것만으로 저장된다) ---
  // 전부 nullable — 하나도 안 골라도 저장되게 한다. 완벽을 요구하면 안 쓴다.
  meal String? // "잘 드심" | "조금 드심" | "거의 못 드심"
  mood String? // "좋으심" | "평소 같으심" | "힘들어하심"

  // --- 더 자세히 (접힌 영역, 전부 선택) ---
  sleep      String?
  bowel      String?
  medication String?
  tasks      String[] // 오늘 한 일 칩

  // 오늘 한마디 — 보호자가 가장 좋아하는 부분
  memo      String?
  // 특이사항 — 값이 있으면 보호자에게 즉시 알림.
  // "알려드릴 일이 있어요"를 골랐을 때만 입력창이 열린다.
  alertNote String?

  // 돌봄 시간 — 1단계에선 선택 기록, 2단계 정산 연동 시 근거가 된다
  workStart String? // "09:00"
  workEnd   String? // "18:00"

  photos Json? // [{url, takenAt}] — 카메라 촬영만

  // 보호자가 읽은 시각 (매니저에게 "확인했어요"로 표시)
  readAt DateTime?

  // 정정 기록 — 원본을 고치지 않고 새 행을 만들어 잇는다(append-only)
  correctsId String?

  @@index([careRequestId, careDate])
  @@index([sitterProfileId])
}

// 빠른 알림 — 돌봄 중에 버튼 하나로 그 자리에서 보내는 알림(§5-4-1).
//
// CareLog와 분리한 이유: 일지는 하루에 하나지만 빠른 알림은 하루에 여러 번 발생하고,
// 발생 시각 자체가 정보다("점심을 몇 시에 드셨나"). 일지 안에 배열로 넣으면
// 시간순 조회·취소·연타 방지를 다루기 번거롭다.
//
// 이 기록들이 그날 CareLog를 자동으로 채우는 재료가 된다 — 매니저가 저녁에
// 따로 일지를 쓰지 않아도 "식사 2회·복약 1회"가 이미 남아 있다.
model CareQuickNote {
  id              String @id @default(cuid())
  careRequestId   String
  sitterProfileId String

  // "meal" | "medication" | "walk" | "hospital" | "sleep" | "custom"
  kind String
  // kind가 custom일 때만 내용이 있다(⚠️ 알려드릴 일이 있어요)
  body String?

  careDate  String // YYYY-MM-DD (KST) — 일지와 묶는 키
  createdAt DateTime @default(now())

  // 1분 안에 취소하면 지우지 않고 표시만 한다 — 보호자가 이미 봤을 수 있어서
  // 조용히 사라지면 "내가 잘못 봤나" 싶게 된다
  canceledAt DateTime?

  readAt DateTime?

  @@index([careRequestId, careDate])
}
```

**민감정보 주의**: 식사·배변·투약은 건강정보다. `CareProfile`과 같은 수준으로 다루고
개인정보처리방침 수집 항목에 반영해야 한다. 돌봄 종료 후 보관 기간도 정해야 한다.

## 7. 화면 구성

### 7-1. 매니저 — 작성 (`/mypage/sitter/log/[careRequestId]`)

**한 화면에 다 들어오고 스크롤이 없어야 한다.** 현장에서 한 손으로 쓴다.

```
┌─────────────────────────────┐
│  8월 3일 토요일              │
│  어머니 (김OO님)             │
│                             │
│  지금 알려드리기 ⚡           │   ← 빠른 알림(§5-4-1)
│  [🍚 식사] [💊 약] [🚶 산책]  │      1탭이면 바로 전송
│  [🏥 병원] [⚠️ 알릴 일]       │
│  ─────────────────────────  │
│                             │
│  오늘 하루 정리 (선택)        │
│                             │
│  식사는 어떠셨어요?           │
│  [🍚 잘 드심][🥄 조금][😐 거의]│   ← 큰 버튼, 한 줄
│                             │
│  컨디션은요?                 │
│  [😊 좋으심][🙂 평소][😟 힘들]│
│                             │
│  오늘 하루는?                │
│  [✅ 별일 없었어요]           │
│  [⚠️ 알려드릴 일이 있어요]     │
│                             │
│  ＋ 더 자세히 남기기 (선택)    │   ← 접혀 있음
│                             │
│  [    오늘 기록 남기기    ]   │
│  어제와 같아요 ↺             │   ← 작은 보조 버튼
│                             │
│  일지는 의무가 아니에요.       │   ← 부담 덜어주는 안내
│  남겨두시면 후기받기가 쉬워져요 │
└─────────────────────────────┘
```

**빠른 알림을 맨 위에 둔다.** 매니저가 이 화면을 여는 대부분의 순간은 "지금 뭔가 알리려고"이지
"하루를 정리하려고"가 아니다. 하루 정리는 아래로 내린다.

- 버튼은 크게(최소 56px) — 40~60대 매니저가 현장에서 누른다
- **저장 버튼 하나**, 아무것도 안 골라도 눌린다
- 이미 쓴 날은 "작성 완료"로 잠기고, 고치려면 "정정 기록 남기기"

### 7-2. 보호자 — 열람 (`/mypage/care-log/[careRequestId]`)

- **달력 뷰**가 기본 — 쓴 날/안 쓴 날이 한눈에 보인다
- 날짜를 누르면 그날 기록. 사진이 있으면 크게
- 특이사항이 있는 날은 달력에서부터 다른 색
- 주간 요약: "이번 주 식사 잘하신 날 5일 / 특이사항 1건"

### 7-3. 알림 연동

특이사항 작성 시 보호자에게 즉시 알림 → [찜 알림 인프라](favorite-alert-spec.md)와 같은 발송 경로를 쓴다.
**이 기능이 알림 인프라를 필요로 하는 두 번째 이유다.**

## 8. 사업모델 연결

돌보다의 현재 수익은 전부 B2B(시설 광고·구독)다. 돌봄일지는 **첫 B2C 유료화 후보**다.

| 후보 | 내용 | 검토 필요 |
|---|---|---|
| 기록 보관 연장 | 기본 3개월 무료, 그 이상 보관은 유료 | 거부감 적음 |
| PDF 리포트 | 월간 돌봄 리포트 PDF (요양병원 제출·가족 공유용) | 실수요 있음 |
| 가족 공유 | 형제자매 여러 명이 같이 보기 | 계정 구조 변경 필요 |
