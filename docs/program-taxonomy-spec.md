# 프로그램 분류 체계 기술서

최종 갱신: 2026-08-01 · 구현: [lib/programTaxonomy.ts](../lib/programTaxonomy.ts) · 빌드: `scripts/build-program-tags.mts`

## 1. 왜 만들었나

공단 상세정보에 **프로그램 운영 123,349행**(27,557개 시설)이 있는데 검색·필터에서 전혀 쓰지 않고 있었다.
치매 어르신 보호자에게 "인지 프로그램을 자주 하는 곳"은 결정적인 기준인데, 그걸 찾을 방법이 없었다.

문제는 프로그램명이 자유 텍스트라는 것이다. **고유 명칭이 52,589개** —
`인지프로그램`·`인지활동`·`인지기능프로그램`·`힘뇌체조`가 전부 사실상 같은 것이다.

## 2. 왜 임베딩(pgvector)이 아니라 규칙 기반인가

`pgvector`가 쓸 수 있는 환경이지만 규칙 기반을 택했다.

| 항목 | 규칙 기반 | 임베딩 |
|---|---|---|
| 커버리지 | 94.3% (실측) | 더 높을 수 있음 |
| 비용 | 0원 | 12만 행 임베딩 비용, 갱신 때마다 반복 |
| 설명가능성 | "이 키워드가 있어서" 즉시 설명 가능 | 어려움 |
| 유지보수 | 키워드 추가로 즉시 개선 | 재임베딩 필요 |

상위 명칭이 뚜렷한 군집을 이루고 있어 키워드로 대부분 잡힌다. **94.3%면 충분하고,
남은 5.7%를 위해 비용·불투명성을 감수할 이유가 없다**고 판단했다.

## 4. 주기 파싱

원본 형식이 `주 3회(1시간)`으로 규칙적이라 **95.4%가 파싱된다**.
일/월/년 단위는 주 단위로 환산한다(일×7, 월÷4.345, 년÷52).

같은 프로그램명이 여러 번 등록된 경우가 많아 **이름 기준 중복 제거 후** 주기를 합산한다.

## 5. 데이터 흐름

```
공단 원본(123,349행)
  → summarizePrograms()  프로그램명 → 태그, 주기 환산, 이름 중복 제거
  → extra.programTags    시설당 태그별 {count, weekly, samples} 저장 (12,119곳)
  → 검색 필터 / 상세 배지
```

**미리 계산해 저장하는 이유**: 검색이 매번 12만 행을 훑을 수 없다.
시설 row 안에 요약만 넣어두면 jsonb 조건 한 번으로 필터된다.

## 6. 검색 필터가 서버에서 도는 이유

클라이언트에서 걸러내면 앞서 받아온 300건 안에서만 찾게 된다.
원예처럼 **전국에 312곳뿐인 태그는 결과가 비어버린다.**
그래서 `/api/facilities?programTags=garden` 으로 전체를 대상으로 서버에서 거른다.

단, 거리·등급순 정렬 시에는 `nearby` API를 쓰는데 여기엔 서버 필터가 없어
클라이언트에서 한 번 더 거른다(그 경우 표시 개수도 실제 결과 수로 바꾼다).

## 7. 갱신 방법

공단 상세정보가 갱신되면:
```bash
npx tsx scripts/build-program-tags.mts          # 미리보기
npx tsx scripts/build-program-tags.mts --write  # 반영
npx tsx scripts/check-program-tags.mts          # 커버리지 점검
```

커버리지가 떨어졌다면 `check-program-tags.mts`가 출력하는
"못 잡은 상위 20개"를 보고 `RULES`에 키워드를 추가한다.
